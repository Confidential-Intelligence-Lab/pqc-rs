# liboqs interoperability

PQC-rs includes a native interoperability adapter backed by the public liboqs
C API. No Python liboqs wrapper is required.

## Supported algorithms

The adapter covers:

- ML-KEM-512;
- ML-KEM-768;
- ML-KEM-1024;
- ML-DSA-44;
- ML-DSA-65;
- ML-DSA-87.

## ML-KEM interoperability

liboqs exposes public derandomized KEM operations through:

    OQS_KEM_keypair_derand
    OQS_KEM_encaps_derand

For each supported ML-KEM parameter set, liboqs reports:

    key-generation seed: 64 bytes
    encapsulation seed:  32 bytes

The PQC-rs provider contract maps these inputs directly as:

    key-generation seed = d || z
    encapsulation seed  = m

The canonical interoperability gate requires byte-for-byte parity between
PQC-rs, liboqs, wolfSSL, and OpenSSL across ML-KEM-512, ML-KEM-768, and
ML-KEM-1024.

Coverage includes:

- deterministic key generation;
- exact public-key encoding;
- exact secret-key encoding;
- deterministic encapsulation;
- exact ciphertext;
- exact shared secret;
- cross-provider decapsulation;
- exact implicit-rejection behavior for modified ciphertexts.

## ML-DSA interoperability

The public liboqs signature API exposes:

    OQS_SIG_keypair
    OQS_SIG_sign_with_ctx_str
    OQS_SIG_verify_with_ctx_str

The tested public API does not expose deterministic ML-DSA key generation or
explicit per-signature randomness.

Therefore liboqs participates in the semantic ML-DSA interoperability matrix
rather than the deterministic byte-exact generation matrix.

The canonical gate verifies:

- raw public-key interchange;
- raw secret-key interchange;
- liboqs-generated signatures verified by PQC-rs;
- PQC-rs-generated signatures verified by liboqs;
- signatures produced using keys generated by either implementation;
- empty and non-empty contexts;
- the 255-byte FIPS 204 context boundary;
- modified-message rejection;
- modified-context rejection;
- wrong-public-key rejection;
- signature mutation rejection;
- malformed signature handling;
- 256-byte context rejection;
- cross-parameter-set rejection.

The canonical report records the unavailable deterministic ML-DSA facilities
as:

    unsupported_by_public_api

This is a provider capability distinction and is not treated as an
interoperability failure.

## Rejection behavior

PQC-rs and liboqs do not always reject malformed ML-DSA inputs at the same
software layer.

For some malformed signatures and oversized verification contexts, PQC-rs
rejects at its API or encoding boundary while liboqs performs verification and
returns cryptographic failure.

The canonical interoperability gate records these rejection modes separately
and requires the security-relevant outcome: the invalid input must not be
accepted.

## Installation

Build and install liboqs as a shared library:

    cmake -S . -B build -GNinja \
      -DBUILD_SHARED_LIBS=ON \
      -DOQS_BUILD_ONLY_LIB=ON \
      -DOQS_MINIMAL_BUILD="KEM_ml_kem_512;KEM_ml_kem_768;KEM_ml_kem_1024;SIG_ml_dsa_44;SIG_ml_dsa_65;SIG_ml_dsa_87"

    cmake --build build
    cmake --install build

Point the adapter at an installation prefix with:

    export OQS_PREFIX=/absolute/path/to/liboqs-prefix

Alternatively, point directly at the installed library with:

    export OQS_LIBOQS_PATH=/absolute/path/to/liboqs.so

Use the corresponding `.dylib` path on macOS.

## Execution

The canonical four-provider interoperability gate is:

    cargo xtask interop-cross --strict

The focused liboqs smoke suite remains available through the generic
interoperability framework.

## Claim boundary

A successful liboqs interoperability result demonstrates the tested
byte-level ML-KEM and semantic ML-DSA interoperability properties for the
recorded liboqs build and PQC-rs revision.

It does not constitute FIPS validation, Common Criteria certification, formal
verification, or an independent security audit.
