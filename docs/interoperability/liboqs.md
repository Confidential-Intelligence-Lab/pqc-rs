# liboqs interoperability adapter

A2.2 adds a Python protocol provider backed by a small C bridge over the public
liboqs C API. No Python wrapper package is required.

## Install liboqs

Build a shared library so the adapter can load it dynamically:

```bash
cmake -S . -B build -GNinja \
  -DBUILD_SHARED_LIBS=ON \
  -DOQS_BUILD_ONLY_LIB=ON \
  -DOQS_MINIMAL_BUILD="KEM_ml_kem_512;KEM_ml_kem_768;KEM_ml_kem_1024;SIG_ml_dsa_44;SIG_ml_dsa_65;SIG_ml_dsa_87"
cmake --build build
cmake --install build
```

When the loader cannot find the library automatically, set:

```bash
export OQS_LIBOQS_PATH=/absolute/path/to/liboqs.dylib
```

Use `.so` on Linux.

Alternatively, point the bridge at an installation prefix containing
`include/oqs/oqs.h` and `lib/liboqs`:

```bash
export OQS_PREFIX=/absolute/path/to/liboqs-prefix
```

## Enable and run

```bash
python3 scripts/configure-liboqs-interop.py auto
cargo xtask interop --provider liboqs --suite liboqs-smoke --strict
```

The smoke suite executes all three ML-KEM and all three ML-DSA parameter sets. It checks external-provider execution, standard object sizes, KEM shared-secret agreement, and signature generation/verification.

## Cross-generated operations

The adapter also exposes operations intended for subsequent cross-provider vectors:

- ML-KEM: `keypair-derand`, `encaps-derand`, and `decaps`;
- ML-DSA: `sign` and `verify`, including context strings when supported by liboqs.

These operations allow future vectors generated by the Rust implementation to be consumed by liboqs and vice versa.

## Claim boundary

The A2.2 smoke suite proves that the liboqs adapter can invoke an independent implementation and that each enabled liboqs algorithm completes its own round trip. It does not yet prove byte-for-byte or cross-generated interoperability with this Rust implementation. That requires a Rust provider and paired cross-provider vectors in the next interoperability increment.
