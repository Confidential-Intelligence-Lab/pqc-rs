## Scope

The candidate covers:

- `pqc-rs-core`, the common traits, typed byte containers, errors, and secret
  containers used by the release;
- `pqc-rs-ml-kem`, implementing FIPS 203 ML-KEM-512, ML-KEM-768, and
  ML-KEM-1024; and
- `pqc-rs-hpke`, implementing RFC 9180 Base and PSK modes with ML-KEM, plus
  experimental pure post-quantum and post-quantum/traditional hybrid KEM
  profiles pinned to `draft-ietf-hpke-pq-05`.

The candidate does not publish ML-DSA, SLH-DSA, the reusable hybrid crate, or
the internal test harness. Those workspace components may appear in assurance
and interoperability tests, but they are outside the `v0.4.0` publication
claim.

RFC 9958 is used as Informational engineering and migration guidance. PQC-rs
does not claim to “implement RFC 9958.” Algorithm and protocol claims are
traced to their applicable normative sources, including FIPS 203 and RFC 9180.
Internet-Draft behavior is explicitly revision-pinned and remains
experimental.

## Feedback requested

Focused reviews are especially valuable in the following areas:

1. **Cryptographic correctness and standards traceability** — FIPS 203
   behavior, input validation, implicit rejection, deterministic test paths,
   and the separation of normative claims from Informational guidance.
2. **HPKE and interoperability** — RFC 9180 Base/PSK behavior, suite and mode
   handling, transcript agreement, ML-KEM integration, and the experimental
   `draft-ietf-hpke-pq-05` profiles.
3. **Rust API and secret ownership** — type boundaries, error behavior,
   feature flags, `no_std`/`alloc`/`std` behavior, accidental copying or
   formatting of secrets, and zeroization expectations.
4. **Security engineering** — malformed-input behavior, secret-dependent
   control flow or memory access, generated code, timing screens, fuzzing,
   memory safety, and evidence reproducibility.
5. **Deployment usability** — installation, examples, target support,
   migration guidance, operational limitations, and any claim that could be
   misunderstood by an evaluator or integrator.

Reviewers need not cover every area. A narrow report grounded in a specific
standard section, code path, platform, or integration is useful.

## Quick start

Clone and verify the exact review target:

```bash
git clone https://github.com/Confidential-Intelligence-Lab/pqc-rs.git
cd pqc-rs
git checkout --detach {{REVIEW_TAG}}

test "$(git rev-parse HEAD)" = "{{REVIEW_COMMIT}}"
```

Run the three in-scope crate test suites:

```bash
cargo test -p pqc-rs-core --all-features
cargo test -p pqc-rs-ml-kem --all-features
cargo test -p pqc-rs-hpke --all-targets --all-features
```

Run the broader workspace and traceability gates:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
python3 scripts/validate-a1-1.py
cargo xtask compliance --strict
```

The full portable assurance campaign is more expensive:

```bash
python3 scripts/validate-stage13.py
./scripts/run-stage13.sh portable
```

Provider-specific interoperability checks require the prerequisites described
under [`docs/interoperability/`](../interoperability/README.md). Reviewers may
also inspect the public GitHub Actions results for the candidate commit.

## Reporting findings

For non-sensitive findings, comment on the review issue or open a focused
GitHub issue and include:

- the candidate tag and commit;
- affected crate, API, file, or standard section;
- expected and observed behavior;
- a minimal reproducer, vector, or trace when available;
- platform and toolchain details; and
- your view of release impact.

Do not post suspected vulnerabilities, exploit details, secret material, or
embargoed findings publicly. Use the repository's private vulnerability
reporting channel and follow [`SECURITY.md`](../../SECURITY.md).

Mailing-list comments are welcome, but actionable implementation findings
should also be captured in GitHub so that their status and disposition are not
lost. Public comments will be acknowledged and classified as release-blocking,
post-release, informational, or out of scope. Sensitive findings will be
reported in the public disposition only at a safe level of detail.

## Change control and completion

The review branch is `release/0.4`. It accepts only stabilization and
review-driven fixes. Concurrent ML-DSA development targets `main` and is not
part of this review.

A material change to a published API, cryptographic behavior, serialization or
wire behavior, normative claim, or release-gating assurance result requires a
new fixed candidate and a restarted review clock. Editorial corrections,
CI-only repairs, and clearly non-semantic documentation updates are logged but
do not automatically restart the 21-day window.

The review closes only after 21 full days, classification of every report,
resolution of all critical and high-severity security or correctness findings,
resolution of all release-blocking conformance or interoperability defects,
and rerun of the complete applicable assurance profile for every critical fix.

## Claim boundary

PQC-rs is pre-release software. Project tests, side-channel screens, compiler
audits, SBOMs, signatures, and reproducible evidence are engineering controls;
they are not formal proof, FIPS or CMVP validation, Common Criteria
certification, or an independent security audit. The candidate should not be
used to protect production secrets without independent review and an
application-specific risk assessment.
