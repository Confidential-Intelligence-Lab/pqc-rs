# PQC-rs 1.0.0

## Release status

PQC-rs 1.0.0 is the first stable coordinated release of the PQC-rs
cryptographic foundation.

The stable compatibility boundary consists of:

- `pqc-rs-core` `1.0.0`
- `pqc-rs-ml-kem` `1.0.0`
- `pqc-rs-ml-dsa` `1.0.0`
- `pqc-rs-slh-dsa` `1.0.0`
- `pqc-rs-hpke` `1.0.0`

PQC-Forge and application-layer crates remain separately versioned and are
outside this stable cryptographic compatibility boundary.

The standalone `pqc-rs-hybrid` placeholder remains deferred beyond the 1.0
boundary.

## Promotion basis

PQC-rs 1.0.0 is promoted from `1.0.0-rc.1`.

Between the immutable RC source and the stable promotion point:

- no cryptographic source files changed in any of the five coordinated crates;
- no stable cryptographic API changed;
- no algorithmic or behavioral correction was required;
- fuzz consumers were migrated to the intended 1.0 API boundary;
- release and assurance documentation was completed;
- repository-generated warning noise was eliminated;
- the complete protected CI and assurance suite passed.

The only manifest changes within the five cryptographic crates after RC1 were
metadata-hygiene changes that do not alter cryptographic behavior or the stable
API contract.

## Stable API contract

The supported 1.x compatibility contract follows
`docs/api/PQC_RS_1_0_SEMVER_CONTRACT.md`.

Feature-gated `internal-api` surfaces are engineering and assurance interfaces
and are explicitly excluded from the stable SemVer compatibility contract.

## Standards coverage

The stable cryptographic release includes:

- ML-KEM — FIPS 203;
- ML-DSA — FIPS 204;
- SLH-DSA — FIPS 205;
- HPKE integration including RFC 9180 profiles and PQC-oriented integration.

Detailed standards evidence and traceability remain in the repository
compliance and generated standards documentation.

## Assurance evidence

The release gate includes repository checks for:

- standards and API review;
- unit and integration testing;
- cross-architecture validation;
- constant-time audit;
- secret hygiene and zeroization;
- Miri and sanitizer-based dynamic analysis;
- bounded fuzzing;
- benchmark smoke testing;
- software-provider interoperability;
- HPKE interoperability and ciphersuite validation;
- release metadata and release-audit policy.

## Publication order

The stable crates are published in dependency order:

1. `pqc-rs-core`
2. `pqc-rs-ml-kem`
3. `pqc-rs-ml-dsa`
4. `pqc-rs-slh-dsa`
5. `pqc-rs-hpke`

ML-KEM, ML-DSA, and SLH-DSA may be published after `pqc-rs-core` is indexed.
HPKE is published after its required stable dependencies are indexed.
