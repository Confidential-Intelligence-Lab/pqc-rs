# PQC-rs 1.0.0-rc.1 Release Candidate

## Status

This record tracks preparation, validation, publication, and closeout of the
first coordinated PQC-rs 1.0 release candidate.

The candidate is not considered published or closed until the registry,
provenance, and post-publication verification fields in this record are
completed.

## Scope

The `1.0.0-rc.1` cryptographic release boundary consists of:

- `pqc-rs-core`;
- `pqc-rs-ml-kem`;
- `pqc-rs-ml-dsa`;
- `pqc-rs-slh-dsa`; and
- `pqc-rs-hpke`.

The following are outside this coordinated cryptographic release:

- `pqc-rs-protocol`;
- `pqc-rs-secure-channel`;
- `pqc-rs-authentication`;
- `pqc-rs-test-harness`; and
- the deferred standalone `pqc-rs-hybrid` placeholder.

PQC-Forge/application crates remain separately versioned.

## Compatibility Boundary

The supported 1.x compatibility commitment is defined by
[`docs/api/PQC_RS_1_0_SEMVER_CONTRACT.md`](../api/PQC_RS_1_0_SEMVER_CONTRACT.md).

Feature-gated `internal-api` interfaces, assurance tooling, benchmarks, test
infrastructure, and private implementation modules are outside the supported
application-facing SemVer contract.

## Standards and Protocol Coverage

The candidate brings the hardened cryptographic foundation onto one coordinated
release line:

- ML-KEM: FIPS 203;
- ML-DSA: FIPS 204;
- SLH-DSA: FIPS 205;
- HPKE: RFC 9180 with post-quantum KEM integration; and
- RFC 9958 engineering guidance and traceability where applicable.

Normative conformance claims remain scoped to the applicable standards.
Repository evidence does not constitute FIPS module validation, formal
verification, certification, or an independent security audit.

## Interoperability Scope

Primitive interoperability evidence and HPKE provider-substitution evidence are
maintained as separate campaigns.

The primitive campaign covers the applicable ML-KEM and ML-DSA evidence across
PQC-rs, wolfSSL, OpenSSL, liboqs, AWS-LC, and Bouncy Castle.

SLH-DSA interoperability is separately scoped to PQC-rs, liboqs, and Bouncy
Castle.

HPKE provider substitution is separately exercised across PQC-rs, liboqs,
OpenSSL, wolfSSL, and AWS-LC.

## Assurance Status

The candidate is subject to the repository release policy and generated
assurance gates, including API review, secret-lifetime/zeroization review,
constant-time and secret-dependency analysis, fuzzing, performance evidence,
validation/certification evidence, architecture snapshots, and release
manifest checks.

The complete applicable release profile must pass against the final candidate
commit before publication.

## Publication Order

Registry publication follows dependency order:

1. `pqc-rs-core`;
2. `pqc-rs-ml-kem`, `pqc-rs-ml-dsa`, and `pqc-rs-slh-dsa` after core is indexed;
3. `pqc-rs-hpke` after `pqc-rs-ml-kem` is indexed.

Each registry-dependent package must be dry-run and reconstructed against the
registry-served dependency versions before final publication.

## Candidate Validation

At minimum, the final candidate commit must pass:

```text
python3 scripts/check-release-metadata.py
cargo xtask api-review --check
cargo check --workspace --all-features
cargo test --workspace --all-features
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

The full release audit remains authoritative for the complete release gate.

## Known Limitations

- The candidate has not received an independent security audit.
- Repository assurance evidence is not equivalent to certification or formal
  verification.
- `internal-api` is unstable and excluded from the supported compatibility
  contract.
- PQC-Forge/application crates are outside this coordinated 1.0 cryptographic
  release.
- The standalone hybrid placeholder is deferred beyond this release boundary.
- Cross-architecture assurance remains subject to the environments available
  for the applicable release campaign.
